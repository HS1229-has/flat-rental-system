Chapter 2: Spring Boot Fundamentals & Core Annotations

1. Inversion of Control (IoC) & Dependency Injection (DI)

In standard Java, an object creates its own dependencies using new Service(). This creates tight coupling. With Spring's Inversion of Control (IoC) container, control is inverted: the Spring Framework instantiates, configures, and manages the lifecycle of beans.

Dependency Injection (DI) is the design pattern through which IoC is achieved. Spring injects required dependencies into classes automatically at runtime.

2. Constructor Injection vs Field Injection (Why Field Injection is Bad)

Why we use Constructor Injection across all our Services:
  • Field Injection (@Autowired private BookingRepository repo;): Cannot make fields final; impossible to instantiate or test without a heavy Spring context; hides dependencies.
  • Constructor Injection (Our Approach): Fields are declared private final (immutable thread safety). In unit tests, we can instantiate the service directly with mock objects using new BookingService(mockRepo, mockWebClient) without booting up Spring!
// Production Pattern Used in BookingService.java
@Service
public class BookingService {
    private final BookingRepository bookingRepository;
    private final WebClient.Builder webClientBuilder;

    // Constructor Injection - completely testable with pure Mockito
    public BookingService(BookingRepository bookingRepository, WebClient.Builder webClientBuilder) {
        this.bookingRepository = bookingRepository;
        this.webClientBuilder = webClientBuilder;
    }
}

Chapter 3: DTO Pattern & Input Validation Architecture

1. Why DTOs (Data Transfer Objects) are Essential

An Entity represents the internal database schema. A DTO represents the public contract between client and API. Exposing Entities directly is an anti-pattern because:

  • Mass Assignment Attack: Malicious users can send JSON payloads containing fields like role: "ADMIN" or status: "CONFIRMED". DTOs restrict input to only permitted editable fields.
  • Data Leakage: Entities often contain internal metadata, audit logs, or password hashes. DTOs ensure only safe attributes are returned.
  • Infinite Recursion: Jackson JSON serializer can enter infinite circular loops when serializing bidirectional JPA relationships (e.g. User ↔ Booking). DTOs eliminate circular dependencies.
  • Schema Independence: Database columns can be renamed or refactored without breaking mobile apps or frontend web interfaces.

3. Complete GlobalExceptionHandler.java Implementation

Location: booking-service/src/main/java/com/flatrental/booking/exception/GlobalExceptionHandler.java

package com.flatrental.booking.exception;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import java.util.List;
import java.util.stream.Collectors;

@RestControllerAdvice
public class GlobalExceptionHandler {

    // 1. Intercepts Jakarta Bean Validation failures (@Valid on DTO)
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ApiError> handleValidationErrors(MethodArgumentNotValidException ex) {
        List<String> errors = ex.getBindingResult().getFieldErrors()
            .stream()
            .map(error -> error.getField() + ": " + error.getDefaultMessage())
            .collect(Collectors.toList());
        
        ApiError apiError = new ApiError(HttpStatus.BAD_REQUEST.value(), "Validation Failed", errors);
        return new ResponseEntity<>(apiError, HttpStatus.BAD_REQUEST);
    }

    // 2. Intercepts Custom Business Domain Exceptions
    @ExceptionHandler(InvalidBookingException.class)
    public ResponseEntity<ApiError> handleInvalidBooking(InvalidBookingException ex) {
        ApiError apiError = new ApiError(HttpStatus.BAD_REQUEST.value(), ex.getMessage(), List.of(ex.getMessage()));
        return new ResponseEntity<>(apiError, HttpStatus.BAD_REQUEST);
    }

    // 3. Fallback for unhandled unexpected server errors (500)
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiError> handleAllExceptions(Exception ex) {
        ApiError apiError = new ApiError(HttpStatus.INTERNAL_SERVER_ERROR.value(), "An unexpected error occurred", List.of(ex.getMessage()));
        return new ResponseEntity<>(apiError, HttpStatus.INTERNAL_SERVER_ERROR);
    }
}

Chapter 5: Professional Git Architecture & Reset vs Revert

1. Git's 4 Logical Areas & Lifecycle Flow

Git does not simply track files; it operates across 4 distinct memory and disk boundaries:

  • Working Directory: The local sandbox on your filesystem where you actively write and edit code files.
  • Staging Area (Index): The intermediate cache where changes are reviewed and prepared using git add <file> before being permanently committed.
  • Local Repository (.git): The local cryptographic commit graph stored on your computer after executing git commit -m "feat: add null validation".
  • Remote Repository (GitHub / GitLab): The shared central server where team members push and sync branches using git push origin feature-branch.

2. Enterprise Branching Strategy

Branch Lifecycle & Protection Engineering Purpose & Rules
main / master Protected. Direct push strictly forbidden. Contains production-ready code deployed to live AWS/production servers. Merges only allowed via approved Pull Requests.
develop Integration branch. Aggregates completed features from multiple developers for staging integration testing.
feature/<name> Short-lived developer branches. Example: feature/booking-null-validation. Created from develop, tested thoroughly, and merged via PR.
hotfix/<name> Emergency branch. Branched directly from main to fix critical production bugs, then cherry-picked/merged into both main and develop.

3. Resolving Merge Conflicts Step-by-Step

Merge conflicts arise when Git cannot automatically reconcile concurrent line modifications across branches. Git inserts conflict markers directly into the file: 

<<<<<<< HEAD (Current Branch - e.g., main)
if (request.getStartDate() == null || request.getEndDate() == null) {
    throw new InvalidBookingException("Dates are mandatory");
}
=======
if (request.getStartDate() == null || request.getEndDate() == null) {
    throw new InvalidBookingException("Start date and end date are required");
}
>>>>>>> feature/booking-validation (Incoming Branch)

Resolution Steps: (1) Open file and discuss with author, (2) Keep desired code and delete markers (<<<<<<<, =======, >>>>>>>), (3) Run git add ., (4) Finalize with git commit -m "fix: resolve booking validation merge conflict".

4. Git Reset vs Git Revert: The Definitive Comparison

The Accounting Ledger Analogy (Master this for the Viva!)
Imagine a corporate bank ledger where an erroneous entry was recorded: "Paid ₹10,000 to John".
• git reset (Tearing the Page Out): Rewinds the timeline and erases history as if the transaction never occurred. In accounting, tearing out a ledger page is an audit violation. If teammates have already copied the ledger, their copies will conflict!
• git revert (Adding an Adjustment Entry): Adds a new entry at the bottom of the ledger: "Reversal adjustment: Refunded ₹10,000 from John". History is preserved, audits pass cleanly, and team collaboration is 100% safe.
Command Working Directory Impact Staging Area Impact When to Use (Industry Rule)
git reset --soft HEAD~1 Changes kept untouched. Changes remain staged! Local only. Modifying commit message or adding forgotten files into previous commit.
git reset --mixed HEAD~1
(Default)		 Changes kept untouched in files. Changes un-staged. Local only. Splitting a large commit into smaller commits.
git reset --hard HEAD~1 Destroys all file changes! Destroyed! Local only. Discarding unwanted experimental code permanently. Never use on pushed commits!
git revert <commit-hash> Applies inverse changes safely. Stages inverse diff. MANDATORY for shared/pushed commits on GitHub. Non-destructive; creates a new commit undoing the mistake.

Chapter 6: Unit Testing Masterclass with JUnit 5 & Mockito

1. What is a Unit Test and Why do we Mock?

A Unit Test validates the behavior of the smallest testable piece of code (typically a single method) in total isolation from external systems such as databases, network sockets, or external microservices.

  • Why not Integration Tests for everything? Running the full Spring Boot application (@SpringBootTest) takes 15–30 seconds per test because it boots Hibernate, embeds an H2 database, and scans beans. In contrast, pure Mockito unit tests execute in 5 to 10 milliseconds!
  • The AAA (Arrange-Act-Assert) Pattern:
    1. Arrange: Prepare mock dependencies, mock data, and define stub behaviors using when().thenReturn().
    2. Act: Invoke the exact business method under test (e.g. bookingService.createBooking(...)).
    3. Assert: Verify expected outcomes using assertEquals(), assertThrows(), and behavior verification with verify().

2. Core Mockito Annotations & Methods

Annotation / Method Underlying Mechanism Project Usage
@ExtendWith(MockitoExtension.class) JUnit 5 extension that initializes Mockito annotations and validates framework rules before each test. Annotated on top of BookingServiceTest and MockPaymentServiceTest.
@Mock Creates a simulated dummy instance of a dependency (returns defaults like null or 0 unless stubbed). @Mock private BookingRepository bookingRepository;
@InjectMocks Instantiates the real service under test and injects all created @Mock objects into its constructor. @InjectMocks private BookingService bookingService;
when(...).thenReturn(...) Configures stub behavior on mock methods. when(bookingRepository.findById(1L)).thenReturn(Optional.of(sampleBooking));
assertThrows(...) Asserts that a specific exception class is thrown when the executable lambda runs. assertThrows(InvalidBookingException.class, () -> service.createBooking(req, 1L));
verify(mock, never()).method(...) Behavior verification: guarantees that a method was NEVER invoked during the execution path. verify(bookingRepository, never()).save(any(Booking.class));

The Initial Test Failure

3. Critical Production Bugs & Code Fixes

Critical Security & Financial Flaws Uncovered by Unit Tests:
  • Flaw 1 (Zero & Negative Amounts): createPayment() accepted zero or negative values. A user could pay ₹0 or -₹5,000 and the system saved the status as COMPLETED, locking properties for free or corrupting account books!
  • Flaw 2 (IDOR Vulnerability in Refunds): initiateRefund(paymentId, currentUserId) took currentUserId as a parameter but never verified if it matched payment.getTenantId()! Any logged-in user could trigger refunds on other people's payments!

Production Fixes in MockPaymentService.java:

// 1. Fix for Zero/Negative Amounts (Lines 30-34):
if (request.getAmount() == null || request.getAmount().compareTo(BigDecimal.ZERO) <= 0) {
    throw new PaymentProcessingException("Payment amount must be greater than zero.");
}

// 2. Fix for Unauthorized Refund IDOR (Lines 108-111):
if (!payment.getTenantId().equals(currentUserId)) {
    throw new PaymentProcessingException("You are not authorized to refund this payment.");
}
Advanced Mockito Insight: UnnecessaryStubbingException
During test authoring, our initial zero-amount test contained: when(paymentRepository.findByBookingId(100L)).thenReturn(Collections.emptyList());
Mockito threw org.mockito.exceptions.misusing.UnnecessaryStubbingException. Why? Because our newly added validation guard throws before the code ever reaches findByBookingId! Mockito strict stubbing detects that the stub was never invoked. Removing the stub proved that the early exit guard works perfectly.

When testing Spring Boot controllers, testing AuthService.registerUser(request) directly in unit tests bypasses Jakarta Bean Validation annotations (such as @NotBlank, @Email, and @Pattern). To achieve 100% test coverage, we created two complementary test suites:

Your Answer: "Mockito 3+ enforces Strict Stubbing to prevent dead code in test suites. Q8: "What is the exact technical difference between git reset and git revert?"
Your Answer: "Git reset rewinds the branch HEAD pointer and modifies past commit history, which can permanently delete commits (especially with --hard). Because it rewrites history, it is only safe for local, unpushed branches. In contrast, git revert is non-destructive: it calculates the inverse diff of a commit and appends a brand new commit to the timeline. It preserves complete history and is the industry standard for undoing changes on shared, pushed remote branches."
Hinglish Samajh: Bank ledger yaad rakho! Reset ka matlab panna faadna (history delete karna) - dangerous agar sabke paas copy ho. Revert ka matlab nayi entry daal ke hisaab barabar karna - 100% safe aur professional standard jo sabke sath sync rehta hai.
