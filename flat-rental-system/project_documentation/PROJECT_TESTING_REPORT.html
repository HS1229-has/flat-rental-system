1. Registration Input Validation Fixes (Auth Service)

During recent testing, registration input vulnerabilities were identified in the Auth Service DTO (RegisterRequest.java). To enforce defensive data validation before persistence, input validation rules were implemented and tested:

A. Indian Mobile Number Validation (phoneNumber)

  • Previous State: phoneNumber was an unvalidated String. Alphabetic strings, wrong lengths, or invalid digits could be submitted.
  • Implemented Validation:
    • @NotBlank(message = "Phone number is required")
    • @Pattern(regexp = "^[6-9]\d{9}$", message = "Phone number must be a valid 10-digit Indian mobile number")
  • Rules Enforced:
    • Must be exactly 10 numeric digits.
    • Must begin with a valid Indian mobile starting digit (6, 7, 8, or 9).
    • Rejects alphabetic/alphanumeric strings (e.g. "abcdefghij", "98765abcde").
    • Rejects incorrect length (e.g. 9 digits "987654321", 11 digits "98765432100").
    • Rejects invalid starting digits (e.g. "0987654321", "1234567890", "5876543210").
    • Rejects null and empty/whitespace-only values.

B. Email Syntax Validation (email)

  • Verified Behavior: Standard Bean Validation behavior was tested against malformed inputs:
    • @abc.com (missing local user part) → Rejected
    • abc@ (missing domain part) → Rejected
    • abc (missing @ symbol and domain) → Rejected
  • Implemented Annotation: @NotBlank(message = "Email is required")
    @Email(regexp = "^[^@\s]+@[^@\s]+\.[^@\s]+$", message = "Email must be valid")
  • Design Decision: Enforces standard local@domain.extension syntax while avoiding overly restrictive domain rules to keep legitimate email providers supported.

To properly verify that invalid inputs are blocked at runtime, two dedicated validation test suites were added:

5. Developer Explanation Guide (For Manager / Interviewer)

Q: "How did you fix registration input validation for phone numbers and emails?"

"In RegisterRequest, I added @NotBlank and @Pattern(regexp = '^[6-9]\d{9}$') on phoneNumber (keeping it as a String). This enforces that only 10-digit Indian mobile numbers starting with 6, 7, 8, or 9 are accepted, while rejecting letters, wrong lengths, and invalid starting digits. For email, I verified that malformed patterns like @abc.com and abc@ are rejected, and enhanced it with standard RFC-compliant regex syntax."

Q: "Why did you need separate validation tests instead of just testing AuthService?"

"Service-level unit tests (AuthServiceTest) call Java methods directly, which completely bypasses Bean Validation (@Valid). To test that validation annotations actually execute, I added two suites: RegisterRequestValidationTest using Jakarta Validator (testing 23 input combinations) and AuthControllerValidationTest using Spring MockMvc (testing that invalid HTTP requests return 400 Bad Request with field errors and 0 database writes)."

Q: "What is the overall test coverage and pass rate now?"

"Across Auth Service and Property Service, we now have 63 passing unit and validation tests with a 100% success rate: 23 Bean Validation tests, 5 Controller MockMvc tests, 15 AuthService tests, 4 JwtUtil tests, and 16 PropertyService tests."
